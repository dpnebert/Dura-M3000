One-off OTA recovery audit

Commit f3160f6c64ac518ecebe0c454e3c66f52391cbe0 · ESP32-S3 · ESP-IDF 6.0.2

Recommendation: hold shipment until a rollback-enabled bootloader, the proposed application changes, and the bench recovery checks have been validated together. The download path already uses the SDK’s safe inactive-slot update mechanism. It does not yet establish that a newly booted controller works, and its BLE handoff and sleep handling have concrete defects. No evidence was found or assumed that an update has already failed.

This is a source audit and an uncommitted local proposal. No firmware was flashed, no OTA image was uploaded or deployed, no customer device was accessed, and no commit or PR was created. The configured firmware URL was not contacted. The proposal targets the exact supplied commit, not an unspecified later branch head.

2. Current end-to-end sequence

StepObserved behavior in the supplied commit
Normal bootinit_nvs() runs, then dura_wifi_init_and_provision() initializes and starts Wi-Fi before meter, board and normal BLE startup. STA_START calls connect. Saved credentials are read and logged, but this path does not start OTA polling.
GestureOn the main menu, raw KEY2 + KEY3 levels held for CONFIG_DURA_BOARD_SETTINGS_HOLD_MS (1500 ms) select the OTA QR screen. These are the two middle physical switches. The ordinary key dispatcher still receives the polled middle-key event; it can navigate away during the hold. The hold firing branch does not re-check the main-menu condition.
Normal BLE shutdownstart_ota_wifi_provisioning() calls gama_blefob_sleep_shutdown(). That implementation deliberately vetoes an established connection or in-flight stack user with INVALID_STATE. The new callback incorrectly accepts INVALID_STATE and continues anyway.
Provisioning BLEnetwork_prov_mgr_init() selects the NimBLE BLE scheme with EVENT_HANDLER_NONE. This correctly avoids irreversibly freeing Bluetooth controller memory. Security 1 uses PoP dura-m3000 and service PROV_M3000; the on-screen JSON matches these values. The stock Espressif provisioning app can be used without changing the customer’s legacy apps.
Credentials and IPThe manager receives/stores credentials and manages the connection attempt. CRED_SUCCESS follows GOT_IP. The application logs failure only; the SDK also exposes a prov-ctrl reset endpoint. A bad password is therefore not proven to make provisioning unrecoverable.
Provisioning endsThe manager auto-stops after successful provisioning/status exchange or its configured timeout. NETWORK_PROV_END describes service shutdown, not independently credential success. The application creates a delayed cleanup task, deinitializes the manager, then starts polling even if deinit failed or no success was tracked.
HTTPS probeA GET opens the endpoint, fetches headers, selects ETag or Last-Modified, truncates it to a 128-byte buffer and closes without consuming the firmware body. Missing both headers prevents OTA. A changed token triggers another, independent GET for the actual image.
Image write and selectionesp_https_ota_begin() chooses the next OTA app slot; esp_https_ota_perform() begins erasing/writing it. finish() ends/verifies the image and calls esp_ota_set_boot_partition(). With the supplied saved configuration, rollback tracking is disabled. There is no project/build identity check in application code.
Pre-reboot stateAfter finish(), the old application commits the server token to NVS, stops/restores Wi-Fi to clear credentials, and restarts. Either local operation can fail after the boot slot has already changed. The logged running version is still the OLD image description.
Return to controllerThe new image boots through the ordinary meter, board and legacy BLE initialization. There is no PENDING_VERIFY health check or mark-valid call. With credentials cleared it waits for a new gesture; with saved credentials it reconnects but still does not automatically poll.

3. Confirmed defects and conditional failure paths

P1 means a shipment blocker for this recovery requirement. P2 means a reproducible conditional defect or a required recovery/usability correction. Conditions below are code-derived; they do not assert that a field failure occurred.

Priority / defectEvidence and practical consequenceProposed correction
P1 · No runtime-failure rollbacksdkconfig explicitly disables CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE; no first-boot verification exists. A well-formed ESP32-S3 image that crashes or hangs after boot is not made safe by a successful download. Merely enabling rollback without adding validation would roll back healthy updates too.Enable rollback in saved config and clean-build defaults; arm a 30 s first-boot reset deadline, require a working controller/board/legacy BLE startup, then mark VALID.
P1 · BLE shutdown veto ignoredfirmware/main/app_main.c#L43-L58 accepts INVALID_STATE; existing gama_blefob_sleep_shutdown() returns it for a live link or busy host. Provisioning then tries to initialize a second NimBLE owner.Require ESP_OK. On a veto restore the existing radio and return to the main screen. If the radio is only partly shut down or provisioning partially starts, reboot with outputs OFF.
P1 · Sleep protection starts too late; outputs are not fencedThe OTA-active flag is set only when polling starts. Provisioning can exceed the 60 s default sleep interval; the board can then call the legacy sleep shutdown/resume machinery while provisioning owns BLE. Direct requested sleep also bypasses the late idle-loop flag check. External Recirc and console activation are not excluded during the new OTA screen.Set OTA-active at gesture admission, use the existing serialized meter OFF/activation fence, and reject sleep in the shared final admission check. Keep this fence until reboot/exit.
P1 · Applied state and credential removal precede healthfirmware/main/dura_ota.c#L146-L152 saves the token and clears credentials before the new image runs. Adding rollback alone would leave the fallback seeing the failed candidate’s token as already applied. Local save/reset errors can also return to the polling loop after the boot slot was selected.Make otadata authoritative; remove ETag installation state. finish() is followed immediately by reboot. Clear credentials only for a confirmed VALID ota_1 image, and retry cleanup on later boots if needed.
P2 · Recovery after interruption is incompleteA network disconnect after provisioning has ended has no reconnect handler. A reset retains Wi-Fi credentials but does not recreate polling. Automatic resume is absent, so a downloaded prefix cannot be presumed to continue.Reconnect Wi-Fi after manager deinit during the active session. After a power cycle, return to ordinary controller operation and repeat the physical gesture/provisioning. Full-download restart is sufficient for one update; no byte-range resumption implementation is required.
P2 · OTA context leak on incomplete transferAfter a successful begin/perform return, the incomplete-data check uses ESP_RETURN_ON_FALSE and returns without abort()/finish(). A truncated/unknown-length response can reach this branch; begin resources remain live.Use one abort cleanup path for every pre-finish failure. Never abort a handle after finish(), which frees it even on error.
P2 · ETag is not installed-image identityProbe and download are separate requests without If-Match. ETag A can be associated with image B. Changing a token can reinstall the same build; equal truncated prefixes can hide a change. Missing tokens block otherwise valid firmware.Use one HTTPS image transfer, compare the downloaded descriptor’s project and ELF build hash before the SDK erases the target, and reject the current or last intact failed build.
P2 · Original image is only temporarily retainedTwo OTA slots preserve the running image during one download. The next update from ota_1 would normally select ota_0 and erase the shipped image. There is no factory app partition.For the explicitly one-off scope, only permit ota_0 → ota_1. ota_1 cannot start a second update. A larger partition table or a dedicated immutable factory image is unnecessary for this shipment.
P2 · Gesture events leak into normal UIThe raw two-key hold and ordinary key dispatch run in the same loop without consuming the chord or its partial release. This allows unintended normal navigation and can turn release/repress into the OTA screen’s SELECT reboot action.Consume the captured chord until BOTH keys release, cancel a partial hold, and switch to the OTA screen only when the handoff succeeds.
P2 · Cleanup treats END as successThe END callback unconditionally attempts OTA; cleanup can fail, and task allocation failure leaves the controller on the OTA screen without a recovery transition.Track CRED_SUCCESS, schedule cleanup once, and reboot to normal operation on cleanup/task-start failure. The manager remains the sole Wi-Fi retry owner while active.
P2 · Clean-build partition defaults are ambiguoussdkconfig.defaults contains both unset and enabled CUSTOM lines, and sets derived PARTITION_TABLE_FILENAME without the authoritative PARTITION_TABLE_CUSTOM_FILENAME. The saved sdkconfig is correct, but a clean configuration must not rely on it.Remove the contradictory line and explicitly select partitions_ota.csv through CUSTOM_FILENAME. Pin the component manifest to the reviewed versions.

Existing shared-NVS risk: init_nvs() already erases the entire NVS partition on NO_FREE_PAGES or NEW_VERSION_FOUND. That is especially harmful during a trial image. The patch prevents this erase while PENDING_VERIFY so initialization failure resets/rolls back. It does not add a schema migration system. The delivered candidate must retain backward-compatible meter/calibration/BLE storage and must not perform destructive migrations before confirmation.

4. What is already safe, and what is optional

The partition table has a two-sector 0x2000-byte otadata region and two 0x300000-byte app slots. ota_0 starts at 0x20000; ota_1 starts at 0x320000. The last declared partition ends at 0x720000, within the fitted 8 MiB flash. The SDK writes the inactive app and changes the selector after verification. A download/power interruption before successful selection normally leaves the running app available. That is different from application-runtime rollback. The SDK already rejects invalid image data, wrong chip/revision and oversized images; the patch does not replace those checks.

Optional improvementWhy it is not a required redesign for this one-off
Unique PoP / unique BLE service nameThe fixed Security 1 PoP is a real shared-secret and nearby-device-selection weakness; it is not evidence of broken provisioning. A device-specific PoP and service suffix are desirable later. For this unit, use physical admission and verify which device is in provisioning mode. Do not switch to Security 0.
Secure Boot, signed OTA, anti-rollback and flash encryptionHTTPS with a certificate bundle and hostname validation is already used. Signed images would protect against server compromise/wrong authorized content, but require provisioning/key-management decisions. Anti-rollback security-version eFuses are different from runtime rollback and can defeat recovery to older firmware. Do not enable or burn eFuses as a quick fix.
RTC time / certificate expiry policyThe saved config enables MBEDTLS_HAVE_TIME but disables HAVE_TIME_DATE. No SNTP requirement should be invented to explain a download that has not failed. If date validation is later enabled, arrange trusted time first. Test actual TLS trust/hostname failures on the bench.
Persistent multi-version job journal, manifest service, per-device authorizationUseful for a fleet or repeated updates. The one-off ota_0 → ota_1 gate and SDK states remove the need for a second NVS transaction journal and a new server API.
Byte-range download resumeFull retry is adequate for a 3 MiB maximum one-off image. Range resume adds offset/hash/version persistence and server-support requirements without fixing first-boot rollback.
A permanent factory/recovery partitionNot needed to retain ota_0 for one update. Would require resizing/reflashing the partition table and preserving a separate recovery application. Two slots do not preserve an original forever if later software removes the proposed one-off restriction.
Nicer progress UI / timed provisioning sessionHelpful customer experience improvements. The existing QR screen and deliberate SELECT/reboot exit can support one assisted update. On-device detailed progress and a fleet monitoring service are not prerequisites.

The stock provisioning protocol already has a credential-failure reset endpoint. The proposed automatic failure-state reset and three connection attempts are a small recovery convenience, not a claim that the baseline could never recover from a wrong password. Validate the exact Espressif app versions on the customer’s iOS and Android phones before shipment.

The one-off restriction is intentional: after a successful update, ota_1 continues ordinary controller operation and refuses another update. After rollback, ota_0 may accept a different corrected build. An intact last failed build is refused before erase; this is not a permanent blacklist of all historical failed builds. A partial subsequent write can replace the old failed descriptor. Automatic update attempts never start merely because the controller reboots or Wi-Fi credentials remain saved.

The descriptor ELF hash is a practical build identifier. It is not a firmware signature or a substitute for HTTPS integrity. A same-project image for the wrong physical board can still be logically incompatible; the release operator must select the correct build and perform the bench checks.

6. Concrete C in the proposal

Boot-slot restriction (the SDK still selects/verifies the inactive partition):

bool dura_ota_update_allowed(void)
{
#if !CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE
    return false;
#else
    const esp_partition_t *running = esp_ota_get_running_partition();
    const esp_partition_t *boot = esp_ota_get_boot_partition();
    const esp_partition_t *next = esp_ota_get_next_update_partition(NULL);
    /* One-off policy: never erase the shipped ota_0 image. Also refuse a
     * second attempt after finish has already selected another boot slot. */
    return !s_pending_verify && running && boot && next &&
           running->subtype == ESP_PARTITION_SUBTYPE_APP_OTA_0 &&
           next->subtype == ESP_PARTITION_SUBTYPE_APP_OTA_1 &&
           running->address == boot->address;
#endif
}

The transfer cleanup and selector transition are explicit:

    do {
        err = esp_https_ota_perform(handle);
    } while (err == ESP_ERR_HTTPS_OTA_IN_PROGRESS && atomic_load(&s_polling));
    if (err != ESP_OK) goto abort;
    if (!esp_https_ota_is_complete_data_received(handle)) {
        err = ESP_FAIL;
        goto abort;
    }
    /* finish verifies the image and selects the boot slot; it frees handle
     * even on failure. Never abort it again after this call. */
    err = esp_https_ota_finish(handle);
    if (err != ESP_OK) return err;
    ESP_LOGI(TAG, "Image staged; rebooting for controller health validation");
    esp_restart();
    return ESP_OK;
abort:
    (void)esp_https_ota_abort(handle);
    return err;
}

Controller validation is separate from download success. The timer is armed before initialization can hang. The health function runs only for a PENDING_VERIFY boot; initial shipped ota_0 boots normally.

static bool controller_boot_healthy(bool normal_ble_started)
{
    if (!normal_ble_started || !s_app_command_queue || !s_app_command_reply_queue ||
        !s_app_command_submit_mutex) return false;
    const uint32_t first = dura_board_healthy_cycles();
    unsigned healthy_samples = 0;
    for (unsigned i = 0; i < 50; ++i) {
        dura_meter_snapshot_t meter;
        bool advertising = false, connected = false;
        bool healthy = dura_meter_get_snapshot(&meter) == ESP_OK &&
                       !meter.pump_enabled && !meter.fault_latched &&
                       meter.operation_mode == DURA_OPERATION_IDLE &&
                       gama_blefob_is_advertising(&advertising) == ESP_OK &&
                       gama_blefob_is_connected(&connected) == ESP_OK &&
                       (advertising || connected);
        healthy_samples = healthy ? healthy_samples + 1 : 0;
        if (healthy_samples >= 20 && dura_board_healthy_cycles() - first >= 20) {
            return true;
        }
        vTaskDelay(pdMS_TO_TICKS(100));
    }
    return false;
}

Successful-cycle counting advances only when output synchronization, LCD rendering/flush and meter snapshot succeed. Health requires about two seconds of safe meter and legacy BLE readiness plus at least 20 new board cycles, with up to five seconds for readiness; the overall first-boot deadline is 30 seconds. This tests startup readiness, not proof of every dispensing/calibration operation. Those remain bench acceptance tests. The command routing primitives must also exist. No pump or valve is actuated as a self-test.

esp_err_t dura_ota_boot_finish(bool controller_healthy)
{
    if (s_pending_verify) {
        if (!controller_healthy) {
            return esp_ota_mark_app_invalid_rollback_and_reboot();
        }
        ESP_RETURN_ON_ERROR(esp_ota_mark_app_valid_cancel_rollback(), TAG, "confirm image");
        ESP_ERROR_CHECK(esp_timer_stop(s_verify_deadline));
        ESP_ERROR_CHECK(esp_timer_delete(s_verify_deadline));
        s_verify_deadline = NULL;
        s_pending_verify = false;
        dura_board_set_ota_active(false);
        ESP_LOGI(TAG, "Controller health check passed; OTA image confirmed");
    }
    const esp_partition_t *running = esp_ota_get_running_partition();
    if (running && running->subtype == ESP_PARTITION_SUBTYPE_APP_OTA_1) {
        esp_ota_img_states_t state;
        ESP_RETURN_ON_ERROR(esp_ota_get_state_partition(running, &state), TAG, "cleanup OTA state");
        ESP_RETURN_ON_FALSE(state == ESP_OTA_IMG_VALID, ESP_ERR_INVALID_STATE,
                            TAG, "unconfirmed image cannot clear credentials");
        /* Retry cleanup on later boots if a reset interrupted it. No success
         * token is written by the downloader. otadata is the authority. */
        return dura_wifi_reset_provisioning();
    }
    return ESP_OK;
}

A successful first boot marks VALID before credentials are cleared. A failed mark-valid call leaves credentials intact and the reset deadline active. Credential cleanup failure after validation is logged, releases the activation fence and is retried on a later boot; it does not turn a working controller into a rollback failure. Bootloader rollback protects the pre-confirmation interval, not arbitrary failures days after an image has been confirmed.
